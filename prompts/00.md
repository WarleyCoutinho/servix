# 🔹 PROMPT 0 — Contrato Técnico e Funcional Obrigatório

> **Este prompt deve ser lido, aceito e seguido antes da execução de qualquer outro prompt, feature ou refatoração do sistema.**

---

## 1️⃣ Fidelidade Absoluta às Regras de Negócio

- Nenhuma regra pode ser inferida, flexibilizada ou assumida
- Toda lógica deve refletir **exatamente** o fluxo definido para:
  - **Roles**
  - **Planos**
  - **Permissões**
  - **Dashboards**
- Qualquer comportamento fora dessas regras é considerado **erro funcional crítico**

---

## 2️⃣ TypeScript Estrito (Obrigatório)

- `strict: true` deve estar habilitado
- É **proibido** o uso de:
  - `any`
  - `unknown`
  - `@ts-ignore`
  - `@ts-expect-error`
- Todos os tipos devem ser:
  - **Explícitos**
  - **Determinísticos**
  - **Reutilizáveis**
- Nenhuma tipagem pode ser implícita ou ambígua

---

## 3️⃣ Tipagem Sempre Referente ao Código e ao Banco

- Não é permitido criar tipos genéricos ou soltos
- Todos os tipos devem:
  - Refletir fielmente o **modelo real do banco de dados**
  - Estar alinhados com **Prisma** e **Zod**
  - Ser utilizados de ponta a ponta (**Backend → API → Frontend**)

### Exemplo válido:

```ts
type UserRole = "admin" | "owner" | "professional" | "client";
```

Zero erros e zero warnings

no-explicit-any

consistent-type-imports

5️⃣ Validação Centralizada

Nenhuma regra pode estar hardcoded em componentes, páginas ou rotas

Todas as validações devem ser:

Centralizadas

Reutilizáveis

Testáveis

Padrão obrigatório:
canAccessFeature({
role,
plan,
feature,
})

6️⃣ Backend como Fonte Única da Verdade

O frontend NUNCA decide permissões

O backend é responsável por:

Validar role

Validar plano

Validar vínculo (propriedade ↔ profissional)

O frontend apenas reflete o estado autorizado

7️⃣ Dashboards e Controle de Visibilidade

Nenhum dado sensível pode ser enviado se não for permitido

As APIs devem:

Retornar somente os dados autorizados

Ser estritamente tipadas por role

Componentes frontend:

Não exibem

Não processam

Não inferem dados que não receberam

8️⃣ Migração Segura e Integridade de Dados

A remoção da role owner_professional deve:

Atualizar dados existentes de forma segura

Garantir integridade referencial

Não quebrar usuários ativos

Nenhuma migração pode gerar estado inconsistente

Se não estiver tipado, não existe.

Se quebrar o ESLint ou o TypeScript, não entra em produção.
